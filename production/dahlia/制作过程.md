# 《黑色大丽花：消失的六天》制作过程

三分钟中文解说短片。AI 情景重现 + 档案照片 + 资料图解，全程在 GitHub Actions 上自动出片。
本文记录**从零到成片的每一步、用到什么文件、跑什么命令**，以及**"第一版没有声音"是怎么定位并修掉的**。

---

## 一、成片规格

| 项目 | 参数 |
|---|---|
| 时长 | 180.000 秒（30fps / 5400 帧，精确无误差） |
| 分辨率 | 1920×1080 |
| 视频 | H.264，CRF 21 |
| 音频 | AAC 48kHz 双声道 **（实测：整体 −21.1 dBFS RMS，峰值 −1.5 dBFS）** |
| 结构 | 6 段解说 / 35 个剪辑片段 / 23 条 AI 生成素材 / 6 张资料卡 / 1 张档案照片 |
| 字幕 | 中文硬字幕（ASS 烧录）+ 独立 SRT |

## 二、事实边界（这个项目最在意的）

- 23 条 AI 素材**只是情景重现**，不是历史影像，画面上永久标注「AI情景重现 · 非历史影像」。
- 伊丽莎白·肖特本人**只用 1947 年警方调查通告里的档案照片**，不用 AI 生成的脸冒充本人。
- 指纹是**示意图**，明确标注「非原始证物图像」。
- 案件按 FBI 公开资料**仍未侦破**，片中不指认凶手。
- 来源：`story.json → sources`（FBI Black Dahlia 档案等）。

## 三、制作流程（每一步对应仓库里的文件）

```
剧本/分镜  →  AI 生成素材  →  素材体检  →  配音  →  剪辑+字幕  →  音频合成  →  成片  →  实测校验
story.json   generate.py    qa/*.jpg    audio/*.mp3  render.py   build_audio.py  render.py  audio-report.json
```

### 步骤 1｜剧本与分镜计划：`story.json`、`screenplay.md`

- `story.json` 是**唯一事实来源**：30 个镜头单元（start/duration 严格 6 秒一格）、6 段解说词、统一风格前缀与负向提示词、事实边界与资料来源。
- 23 个 `kind: "agnes"` 走 AI 生成；6 个 `kind: "graphic"` 是程序绘制的资料卡；1 个 `kind: "archive"` 用档案照片。
- `generate.py --validate` 会校验计划完整性 + 每段配音的 SHA-256 是否与剧本文字一致，**计划或配音对不上就直接拒绝开工**。

### 步骤 2｜生成 AI 素材：`generate.py`、`agnes_video.py`、`throttle.py`

- 只调用指定模型 `agnes-video-v2.0`（换模型即报错）。
- 免费额度是 1 分钟 1 次创建：`throttle.py` 用 75 秒共享节流 + 服从服务端 `Retry-After`，`generate.py` 支持任务编号断点续跑。
- 每条素材的生成结果带**请求哈希、字节数、SHA-256、CDN 地址**，写进 `results.json`——这是后面能"不重新生成就复现"的关键。

### 步骤 3｜素材体检：`qa/`、`results.json`

- 每条素材每秒抽 2 帧生成接触印相（`qa/Sxx.jpg`），人工可查。
- 这次实际修掉的问题（都写在 `README.md` 里）：S06 指纹纹理错误→叠加标注示意图；S09 改用档案肖像；S13 只保留 1.4 秒后的背影；S17/S25 避开后段错误纹理与伪字。

### 步骤 4｜配音：`audio/N01–N06.mp3`、`audio/manifest.json`

- 6 段中文解说，声音由用户在试听里选定（`voice_id: voice-00`，zh-CN）。
- `manifest.json` 记录每段的**文字与文件 SHA-256**，渲染时逐条比对，防止"画面是这版、配音是上一版"。

### 步骤 5｜剪辑与字幕：`render.py`、`align_audio.py`

- 剪辑表 `CUTS` 是**人工审过的事件级 EDL**（不是关键词猜片段）：每段解说对应哪几段素材、从素材的第几秒进，都写死在代码里。
- 35 个片段顺序拼接，首尾帧号严格对齐 0–5400，不允许空隙或重叠（有校验，出错即失败）。
- 字幕时间：优先用 `faster-whisper` 本地 ASR 对轨（`align_audio.py`，不外传音频），置信度不足的段落**保留审定剧本文字 + 停顿估算时间**，并在 `alignment-report.json` 里如实标注方法。

### 步骤 6｜音频合成：`build_audio.py`（**本次重写**）

三条轨：解说 + 原创配乐（`generate_horror_bgm.py` 程序合成，无版权）+ 音效（`write_sfx` 合成）。

### 步骤 7｜成片与校验：`render.py` → `delivery/`

烧录字幕、封装 AAC，然后**对成品本身做实测**（见下节）。

## 四、"视频没声音"：定位与修复

### 症状

上一版成片（`黑色大丽花_三分钟_初版.mp4`，46 MB）播放时听不到声音。

### 根因

旧版把解说、配乐、音效全部塞进**一条超长 ffmpeg 滤镜链**里合成：

```
adelay → amix → sidechaincompress → amix → loudnorm
```

而成品校验（旧 `render.py` 的技术检查）**只看容器字段**：音轨是 AAC、48kHz、双声道、能解码，就算通过。
**它从来没有测量过一个音量数字。** 也就是说：一条存在但听得见或听不见的音轨，都能一路绿灯出片。

我在本地用**仓库里真实的六段配音**复刻了同一条滤镜链做对照（ffmpeg 4.2.2 与 7.0.2 两个版本）：

- 混音本身在这两个版本上能出声（约 −20 dBFS）；
- 但云端那次运行用的是 runner 上另一个 ffmpeg 版本，**本环境下载不到 Actions 的产物与日志**（artifact 存储被网络策略拦截），无法对原文件做 A/B 测电平；
- 能确定的是：**整条流水线没有任何一道关卡会拦住"无声"**，这才是它会被交付出去的根本原因。

### 修复

1. **`build_audio.py`：把混音从滤镜链搬进 numpy**
   - 解说解码后按**精确采样点**落轨（不再依赖 `adelay` 大延迟）；
   - 配乐用**本地计算的包络**做闪避（不再依赖 `sidechaincompress`）；
   - 响度归一用**显式 RMS 目标 + 显式峰值上限**（不再依赖 `loudnorm` 的内部测量）；
   - 同样的输入，在任何机器上得到**逐位一致**的结果。
2. **加"静音闸门"**：整体电平、波峰因数、静音占比、**逐段解说电平**，任一项不达标就**直接抛错，不许出片**。
3. **成品也必须过闸**：`render.py` 在封装完成后，对**最终 mp4**（不是中间 wav）重新测一遍，不达标直接失败。
4. **回归测试**：`production/tests/test_dahlia_audio.py` 用标准音、纯静音、"半段静音"三种信号验证闸门真的会拦。

### 实测结果

本地（真实配音，混音阶段）：

```
整体：−21.08 dBFS RMS   峰值 −1.51 dBFS   静音占比 0.56%
逐段：N01 −21.11  N02 −21.15  N03 −20.89  N04 −20.59  N05 −20.17  N06 −20.84 dBFS
```

云端出片后**在最终 mp4 上复测**（`delivery/final-audio-report.json`）：

```
整体：−21.09 dBFS RMS   峰值 −1.52 dBFS   静音占比 1.1%（片头 + 片尾 1.5 秒淡出）
逐段：N01 −21.12  N02 −21.17  N03 −20.91  N04 −20.61  N05 −20.19  N06 −20.85 dBFS
规格：1920×1080 / 30fps / 5400 帧 / AAC 48kHz 立体声 / 48.1 MB / 完整解码通过
```

两次数值几乎一致，说明新的混音**换机器也能复现**——这正是把混音从"依赖 ffmpeg 内部测量"改成"显式计算"的目的。

## 五、如何复现（两种）

### 方式 A：GitHub Actions 出片（推荐）

1. 把 `production/dahlia/dahlia-audio.workflow.yml` 放到仓库的 `.github/workflows/dahlia-audio.yml`。
   （当前 GitHub 授权没有 `workflows` 权限，代理无法代写这个目录，需要你手动放一次。）
2. Actions → **Black Dahlia · 有声成片** → Run workflow。
3. 约 10–20 分钟后在页面底部 Artifacts 下载 `黑色大丽花-三分钟-带声音`。
4. 流程会**自动把实测报告 commit 回分支**：`production/dahlia/delivery/`。

> 素材不会重新生成：`fetch_sources.py` 按 `results.json` 里的 SHA-256 把 23 条已生成素材拉回来，哈希对不上直接报错，绝不拿别的画面顶替。

### 方式 B：本地出片

```bash
pip install pillow numpy faster-whisper      # 另需 ffmpeg / ffprobe、中文字体（Linux: fonts-noto-cjk）

python3 production/dahlia/fetch_sources.py --dest work/dahlia/clips   # 取回已生成素材
python3 production/dahlia/render.py \
  --sources work/dahlia/clips --work work/dahlia \
  --output "work/dahlia/黑色大丽花_三分钟_带声音.mp4"
```

只想单独重做/试听音频：

```bash
python3 production/dahlia/build_audio.py --work work/dahlia --output work/dahlia/soundtrack.wav
```

## 七、2026-09-10 复核：两件之前悬着的事，结了

| 审片报的"35 处画面冻结"到底几处是真缺陷 | **0 处**：13 处是信息卡/档案照/片尾卡（本来就静止），22 处是慢速运镜被 16×16 严阈值误判。已给 `review_film.py` 加 64×64 复核（`verdict` 字段 + 实测标定阈值 0.15） |

## 八、仍然没做完的事（如实记录）

- **视觉逐帧审片未完成**：工具只做抽样图检查（每 5–10 秒一帧）与黑帧/冻结帧/亮度的自动判定，
  构图、字幕错字、AI 画面畸变仍要人看对照表。2026-09-09 那份记录里人工核对过一遍，
  2026-09-10 只复核了自动判定部分。
- **逐字听检：工具已就位，还没在成片上跑出数字**。`production/verbatim_check.py`
  会解码成片、按章节切段转写（不给 `initial_prompt`）、与剧本算字错率。它要下载
  whisper 模型，本沙箱连不上 Hugging Face，得在 GitHub Actions 上跑
  （模板 `production/verbatim-check.workflow.yml`，结果 commit 回
  `delivery/verbatim-check.json`）。在那之前，下面这条仍然成立：
  闸门能证明"有声、电平正常、每段都有声"，但**不证明配音念的字和剧本一字不差**。
  本次出片的 ASR 对轨覆盖率（见 `delivery/technical-report.json`）：

  | 段落 | 方法 | 覆盖率 |
  |---|---|---|
  | N01 / N02 / N03 / N06 | 停顿估算 | 0.72 / 0.15 / 0.68 / 0.13 |
  | N04 / N05 | ASR 对轨 | 0.98 / 1.00 |

  覆盖率低的四段保留审定剧本文字、用停顿估算时间，需要人工听一遍确认字幕与配音同步。
- 成片（48.1 MB）**已 commit 进本分支的 `交付/`**，方便直接从仓库取片；中间产物仍在 Actions 工作区，不进 Git。仓库只保存输入、小尺寸检查图、成片与制作元数据。
